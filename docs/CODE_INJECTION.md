# Инъекция кода и перехват функций (Code Injection & Hooking)

Инъекция кода — ключевой механизм для создания продвинутых трейнеров и патчей на лету (бесконечные патроны, God Mode, отключение кулдаунов). В данном документе детально описаны низкоуровневые алгоритмы внедрения кода в Engine+.

---

## 1. Выделение памяти в целевом процессе (`Remote Alloc`)

Для размещения пользовательского шеллкода требуется выделить страницу с правами исполнения (`PROT_READ | PROT_WRITE | PROT_EXEC`).

### 1.1. На Windows
Выполняется нативно через WinAPI:
```rust
let addr = VirtualAllocEx(
    process_handle,
    preferred_address, // попытка выделить в пределах +-2GB
    size,
    MEM_COMMIT | MEM_RESERVE,
    PAGE_EXECUTE_READWRITE,
);
```

### 1.2. На Linux (Через `ptrace` + Syscall Injection)
В Linux отсутствует аналог `VirtualAllocEx`. Engine+ использует алгоритм инъекции системного вызова `sys_mmap`:

```
1. PTRACE_ATTACH к одному из потоков процесса.
2. Сохранение регистров процессора через PTRACE_GETREGS (RIP, RSP, RAX и т.д.).
3. Сохранение 8 байт по текущему адресу RIP.
4. Запись опкода `syscall; int3` (0x0F 0x05 0xCC) по адресу RIP.
5. Настройка регистров под вызов sys_mmap:
   - RAX = 9 (номер сисколла mmap в x86_64)
   - RDI = 0 (любой адрес)
   - RSI = size (размер страницы, 4096)
   - RDX = 7 (PROT_READ | PROT_WRITE | PROT_EXEC)
   - R10 = 0x22 (MAP_PRIVATE | MAP_ANONYMOUS)
   - R8  = -1 (fd)
   - R9  = 0 (offset)
6. PTRACE_CONT до срабатывания точки останова INT3.
7. Считывание RAX через PTRACE_GETREGS -> это выделенный виртуальный адрес!
8. Восстановление оригинальных 8 байт памяти и оригинальных регистров.
9. PTRACE_DETACH.
```

### 1.3. Через Kernel Driver
Если активен LKM-драйвер, память аллоцируется непосредственно из ядра через `vm_mmap` в структуре `task->mm` целевого процесса без остановки потоков.

## 2. Размещение в пределах ±2 ГБ (Оптимизация Jump)

В архитектуре x86_64 стандартная инструкция длинного перехода `jmp rel32` имеет размер **5 байт** (`E9 xx xx xx xx`) и может адресовать смещение только в пределах **±2 ГБ** от текущей инструкции.

Если выделить память в случайном месте (дальше 2 ГБ), приходится использовать длинный 14-байтный переход:
```asm
FF 25 00 00 00 00 [8 байт 64-битного абсолютного адреса]
```
14 байт часто затирают соседние инструкции, ломая логику программы.

### Решение Engine+:
При вызове `memory.alloc(size)` сканируются свободные регионы памяти процесса **в радиусе ±2 ГБ от точки хука**. Память запрашивается по конкретному базовому адресу (`MAP_FIXED_NOREPLACE` в Linux или точный адрес в `VirtualAllocEx`), что гарантирует возможность использования **компактного 5-байтового перехода**!

## 3. Архитектура трамплина (Trampoline Hook)

Когда пользователь пишет:
```asm
"game.exe"+0x1024A:
jmp my_code
nop
return_here:
```

Engine+ выполняет:
1. **Декодирование инструкций** в точке хука с помощью `iced-x86`.
2. Если суммарная длина перекрываемых инструкций больше 5 байт (например, 7 байт), оставшиеся 2 байта заполняются опкодами `NOP` (0x90).
3. Скопированные оригинальные инструкции переносятся в начало выделенного блока `newmem` (с коррекцией RIP-относительной адресации, если инструкции использовали `rip + offset`).
4. В конец блока дописывается обратный прыжок `jmp return_here`.
5. Память помечается как защищённая от случайной перезаписи.

---

## 4. Безопасное снятие хука (Un-hooking)

При отключении скрипта или выгрузке чит-таблицы:
1. Процесс кратковременно ставится на паузу (`SIGSTOP` в Linux или `NtSuspendProcess` в Windows).
2. Оригинальные байты возвращаются на своё место атомарно.
3. Выделенная память освобождается через `sys_munmap` / `VirtualFreeEx`.
4. Процесс возобновляет работу (`SIGCONT` / `NtResumeProcess`).
